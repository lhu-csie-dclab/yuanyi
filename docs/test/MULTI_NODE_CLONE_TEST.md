# Multi-Node Fresh-Clone Deployment & Concurrent Multi-GPU Test

This document records an end-to-end validation run: simulating a brand-new open-source user
who clones this repository from GitHub, deploys it on multiple independent machines, and
confirms both (a) that inference requests are actually served by distinct physical GPUs across
the swarm, and (b) that a single entry-point node correctly distributes concurrent load to
other nodes instead of queueing everything behind its own GPU.

> [!NOTE]
> Results below are from re-running this test on **2026-08-21**, at commit `6b1b4e2` (`main`),
> which includes three PRs merged since the previous revision of this document (`bdfc4d7`):
> the Vue 3 + Vite + Tailwind dashboard rewrite (#7), pinning the Go toolchain to `1.26.6` to
> close CVE-2026-39822/CVE-2026-42505 (#8), and closing two remote-code-execution vectors in
> the mooncake-proxy tunnel and vLLM launch command plus docker-compose container hardening
> (#9). This run re-verifies the same fresh-clone and multi-GPU-distribution methodology as
> the previous revision end-to-end against the new code, rather than assuming it still holds.

For raw single-node throughput/latency numbers under sustained load, see
[`BENCHMARK_RESULTS.md`](BENCHMARK_RESULTS.md) (NVIDIA AIPerf, 10,000 requests). This document
instead focuses on **multi-node, multi-GPU correctness**: does a fresh `git clone` really work,
does the swarm really use every physical GPU it claims to have, and does hitting one node's
gateway actually spread concurrent load across the swarm rather than piling it onto one card.

## 🧪 Test Methodology

1. On each of the 10 nodes, cloned this repository fresh into a clean directory (`/root/0821`,
   dated to today's test run and kept separate from the previous run's `/root/0820-2`
   deployment):
   ```bash
   git clone https://github.com/lhu-csie-dclab/yuanyi.git
   ```
2. Populated only what a real new participant would need, per
   [`P2P_NETWORK.md`](../P2P_NETWORK.md) and `.env.example`:
   - `swarm.key` — reused the existing swarm's private-network key (distributed out-of-band to
     participating nodes, as documented; **not** committed to the repo).
   - `.env` — `ABS_MODEL_PATH` (pointing at locally available model weights),
     `SERVER_ADDRESS` (existing bootstrap multiaddress), `IFACE`, `CLIENT_WEB_PORT`, matching
     `.env.example`.
   - `identity.key`, `stats.json`, `peers.db` — left empty/absent and generated by the
     application itself on first run, exactly as a first-time user would experience (confirmed:
     all 10 nodes came up with brand-new PeerIDs, distinct from the previous run's deployment).
3. Built and started with the stock compose file:
   ```bash
   docker compose up -d --build
   ```
   This is the first real end-to-end exercise of the 3-stage `Dockerfile` (Node/Vite dashboard
   build → Go 1.26.6 build → CUDA runtime) added in PR #7/#8 against this fleet's actual GPU
   hardware, not just CI.
4. Cut over from the previous run's deployment (`docker compose down` in `/root/0820-2`) before
   bringing the new one up, so only one container held each node's GPU at a time.
5. Verified P2P mesh formation via each node's `/api/peers` and `/api/node_info` endpoints, and
   vLLM readiness via `/health` (port `8100`).
6. Ran three separate request patterns while sampling each node's own
   `vllm:request_success_total` Prometheus counter (port `8100/metrics`):
   - **Sequential**: one request to each node's own gateway, in turn.
   - **All-10-concurrent**: all 10 nodes' gateways hit at the same time.
   - **Single-entry-point concurrent**: multiple concurrent requests sent to **only one**
     node's gateway, to verify that node distributes the load itself.

### Request Parameters

```json
{
  "model": "Qwen3-4B-AWQ",
  "messages": [{"role": "user", "content": "Say hello in one short sentence."}],
  "max_tokens": 150,
  "temperature": 0.7
}
```
`max_tokens` was raised to 180 for the concurrent test patterns to widen the generation
window for measurement.

### 3. Single-Entry-Point Distribution Test

9 concurrent requests were sent to **one node's gateway only** — no other node's endpoint was
touched directly. This exercises the concurrency-aware dispatcher from PR #4 (local-vs-remote
decision based on whether the local GPU is *currently free* — `localBusy`, `atomic.Bool` +
`CompareAndSwap` — not just whether it is *healthy*), now re-verified against the code shipped
in PR #7–#9.

**Live dispatcher decision log, captured from the target node's own `/api/logs`:**
```
[PROXY] 本地 vLLM 處理 (模型: Qwen3-4B-AWQ)                                x1
[PROXY] 本地 vLLM 忙碌中 (模型: Qwen3-4B-AWQ)，分派至 P2P 遠端節點...          x8
[PROXY] P2P 備援轉發 Qwen3-4B-AWQ -> 遠端節點: 12D3KooW... (嘗試 1/3)         x8
```
("忙碌中" = busy; "分派至 P2P 遠端節點" = dispatched to a P2P remote node; "備援轉發" = fallback
forwarded.)

| Result | Value |
| :--- | :--- |
| Requests sent, all to the same single node | 9 |
| Successful responses (`HTTP 200`) | 9/9 |
| Response time range | 1.91s – 1.98s (a ~70ms spread across all 9, not 9x one request's latency) |
| Kept local (per dispatcher log) | 1 |
| Dispatched to P2P peers (per dispatcher log) | 8 |

**Independent confirmation via each node's own vLLM execution counter** (`vllm:request_success_total`,
cumulative since container start; baseline after Sections 1–2 was **2** on all 10 nodes, so any
increase beyond that baseline in this section reflects only the 9 single-entry-point requests):

| Node | Count before | Count after | Delta |
| :--- | :---: | :---: | :---: |
| Target node (101) | 2 | 3 | +1 (local win) |
| 8 other nodes | 2 each | 3 each | +1 each |
| 1 other node | 2 | 2 | +0 (not selected this round) |

All **9 requests are individually accounted for** — 1 local execution plus 8 remote nodes each
executing exactly one dispatched request, with zero requests queued twice on the same GPU and
zero unaccounted-for requests. This is a cleaner result than the previous run (which saw two
requests land on the same remote GPU): this run's 9 requests spread across 9 distinct physical
GPUs (target + 8 remote) with perfectly even one-request-each distribution.

A request queued behind another on the same GPU would add roughly one full generation's worth
of latency (~2s) per position in the queue; 9 requests completing within a ~70ms window of each
other is only possible if the work was genuinely spread across multiple GPUs running in
parallel, not serialized on one.

## ✅ Conclusion

A completely fresh `git clone` of this repository at `6b1b4e2` — now including the Vue 3
dashboard rewrite, the pinned Go 1.26.6 toolchain, and the mooncake-proxy/docker-compose
security hardening from PR #7–#9 — configured only with the values a real new swarm participant
would need (bootstrap address + shared private-network key), builds via the new 3-stage
Dockerfile and runs correctly via the stock `docker-compose.yml`, joins the existing P2P mesh,
and serves inference from its own local GPU. Across 10 independently deployed nodes on 2
separate physical hosts, every node's GPU was independently confirmed active while correctly
serving real chat completion requests. A single node's gateway continues to correctly recognize
when its own GPU is already busy and automatically distributes concurrent overflow to other
nodes in the swarm — verified both via the dispatcher's own decision log and via independent
execution counters on the receiving nodes' vLLM instances, this run showing a perfectly even
one-request-per-GPU spread across all 9 concurrent requests.
