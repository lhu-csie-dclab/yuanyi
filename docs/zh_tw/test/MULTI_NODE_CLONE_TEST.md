# 多節點全新 Clone 部署與併發多卡測試（繁體中文）

本文件記錄一次端到端驗證：模擬一個完全陌生的開源使用者，從 GitHub clone 這個 repo、部署到多台
獨立機器上，並確認 (a) 推論請求真的是由 Swarm 裡不同的實體 GPU 各自處理，以及 (b) 單一入口節點
在收到併發請求時，真的會自動分派給其他節點，而不是全部排在自己的 GPU 隊列裡。

> [!NOTE]
> 以下結果是在 commit `bdfc4d7`（PR #4「把本機/遠端派發改成依併發狀態決定，而不是只看健康狀態」）
> 之後重新跑的。第 2、3 節取代了這份文件在該修正之前的舊版內容——第 3 節描述的「單一入口自動分派」
> 行為在舊版當時根本還不存在。

（完整英文版：[`docs/test/MULTI_NODE_CLONE_TEST.md`](../../test/MULTI_NODE_CLONE_TEST.md)）

單節點在持續高負載下的吞吐量/延遲數據請見 [`BENCHMARK_RESULTS.md`](BENCHMARK_RESULTS.md)。本文件
著重的是**多節點、多 GPU 的正確性**：全新 `git clone` 是否真的能跑起來、Swarm 是否真的用到了它
宣稱擁有的每一張實體 GPU，以及打單一節點的 gateway 是否真的會把併發負載分散出去，而不是全部堆在
一張卡上。

---

## 🖥️ 測試環境

| 項目 | 內容 |
| :--- | :--- |
| 節點數量 | 2 台獨立實體主機，共 10 個獨立容器（每台主機 5 個） |
| 每節點 GPU | 1x NVIDIA **Quadro RTX 4000（8GB VRAM）**，PCIe passthrough 直通給每個容器 |
| 容器執行環境 | LXC（非特權容器），Docker **29.6.1**，Docker Compose **v5.3.1** |
| 推論基礎映像 | `nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.2.1-cuda13`（CUDA 13） |
| Go 工具鏈（容器內建置） | `go1.26`（Alpine builder stage） |
| 測試模型 | `Qwen3-4B-AWQ`（4-bit AWQ 量化） |
| Repository commit | `bdfc4d7`（`main`） |
| 網路模式 | Docker `network_mode: host`，10 個節點全部加入同一個私有 libp2p Swarm（共用 `swarm.key`） |

> [!NOTE]
> 每個節點都使用這個 repo `main` 分支上**完全未修改**的原始 `Dockerfile` / `docker-compose.yml`，
> `server_mode.enabled` 維持預設值（`false`）——也就是純 client 模式，沒有動任何程式碼。

## 🧪 測試方法

1. 在 10 個節點上分別把這個 repo 全新 clone 到乾淨目錄。
2. 只填入一個真實新加入者會需要的東西（`swarm.key` 沿用既有網路、`.env` 只填
   `ABS_MODEL_PATH`/`SERVER_ADDRESS`/`IFACE`/`CLIENT_WEB_PORT`），`identity.key`/`stats.json`/
   `peers.db` 全部留給程式自己在第一次啟動時產生。
3. 用原始的 `docker-compose.yml` 建置並啟動。
4. 透過 `/api/peers`、`/api/node_info` 驗證 P2P 網格成形，`/health`（8100 埠）確認 vLLM 就緒。
5. 執行三種請求模式，同時取樣 `nvidia-smi`，第三種模式額外比對各節點自己的
   `vllm:request_success_total`（vLLM 自己的 Prometheus 執行計數器）：
   - **逐一測試**：依序對每個節點自己的 gateway 各送一次請求。
   - **10 台全部併發**：10 個節點的 gateway 同時被打。
   - **單一入口併發**（新）：多筆併發請求只送給**其中一個**節點的 gateway，驗證它會不會自己
     把負載分出去。

### 請求參數

```json
{
  "model": "Qwen3-4B-AWQ",
  "messages": [{"role": "user", "content": "<每次測試提示詞不同>"}],
  "max_tokens": 150,
  "temperature": 0.7
}
```
併發測試把 `max_tokens` 拉高到 180-200，方便 `nvidia-smi` 取樣有更長的生成視窗。

## 📊 測試結果

### 1. 部署與網格成形（全部 10 個節點）

| 檢查項目 | 結果 |
| :--- | :--- |
| `git clone` 到 commit `bdfc4d7` | ✅ 10/10 |
| `docker compose up -d --build` 成功 | ✅ 10/10 |
| Gateway `/health` → `200` | ✅ 10/10 |
| vLLM `/health`（8100 埠）暖機後 → `200` | ✅ 10/10 |
| P2P Peer 探索 | ✅ 10/10，每個節點都看到其餘全部 9 個節點（全連通網格） |

### 2. 逐一測試 + 10 台全部併發（每台各自處理自己的請求）

| 模式 | 請求數 | 成功 | 觀察到的 GPU 使用率 | 回應時間 |
| :--- | :---: | :---: | :---: | :---: |
| 逐一測試（一次一台） | 10 | 10/10（`HTTP 200`） | 每台各自獨立跑到 100% | 1.6s – 2.5s |
| 10 台全部併發 | 10 | 10/10（`HTTP 200`） | 多點快照在每台主機上都捕捉到 2 個節點同時 100% | 2.07s – 2.19s |

再次確認是 10 張不同的實體 GPU 在服務，不是同一張卡在應付全部流量。

### 3. 單一入口併發分派測試（新）

9 筆併發請求**只送給一個節點的 gateway**——完全沒有直接打其他任何節點的端點。這正是在驗證
PR #4 的修正：dispatcher 判斷「要不要走本機」現在看的是本機**當下有沒有空**
（`localBusy`，`atomic.Bool` + `CompareAndSwap`），而不是只看本機健不健康。

**從目標節點自己的 `/api/logs` 抓到的即時 dispatcher 決策日誌：**
```
[PROXY] 本地 vLLM 處理 (模型: Qwen3-4B-AWQ)                                x2
[PROXY] 本地 vLLM 忙碌中 (模型: Qwen3-4B-AWQ)，分派至 P2P 遠端節點...          x7
[PROXY] P2P 備援轉發 Qwen3-4B-AWQ -> 遠端節點: 12D3KooW... (嘗試 1/3)         x7
```

| 結果 | 數值 |
| :--- | :--- |
| 送出的請求數（全部打同一個節點） | 9 |
| 成功回應（`HTTP 200`） | 9/9 |
| 回應時間範圍 | 1.93s – 2.00s（基本上就是單一請求的延遲，不是 9 倍） |
| 留在本機（依 dispatcher 日誌） | 2 |
| 分派到 P2P 遠端節點（依 dispatcher 日誌） | 7 |

**用各節點自己的 vLLM 執行計數器（`vllm:request_success_total`）獨立佐證**（此計數器是容器啟動
以來的累計值；先前逐一測試 + 10 台全部併發測試已經讓每台節點的基準值落在 2，若某節點數值高於 2，
代表它在本次測試中額外執行了推論）：

| 節點 | 執行計數 | 是否高於基準 |
| :--- | :---: | :---: |
| 目標節點 | 4 | ✅（本測試貢獻 2 次本機執行） |
| 其餘 5 個節點 | 3、3、4、4、8 | ✅ 全部高於 2 的基準值 |
| 其餘 4 個節點 | 2 | 落在基準值（這輪沒被選中） |

除了目標節點之外，至少還有 **5 台不同的實體 GPU** 執行計數高於單靠逐一測試/全部併發測試會產生
的數值——直接證實那 7 筆被分派出去的請求，真的在好幾台不同的遠端機器上執行，不是留在目標節點
本機，也不是在排隊。

如果請求是排在同一張 GPU 後面依序執行，每多排一個位置大約要多等一次完整生成的時間（約 2 秒）；
9 筆請求能在彼此相差不到 70 毫秒的時間內全部完成，只有真的分散到多張 GPU 平行執行才做得到，不可能
是在同一張卡上排隊處理。

## ✅ 結論

一個完全全新 `git clone` 下來的 repo，只填入真實新參與者會拿到的資訊（Bootstrap 位址 + 共用私網
金鑰），透過原始 `docker-compose.yml` 就能正確建置與運行、加入既有的 P2P 網格，並用自己本機的
GPU 提供推論。在 2 台獨立實體主機上分別部署的 10 個節點中，每個節點的 GPU 都被獨立確認為真的在
運作，並正確服務真實的對話請求。不僅如此，單一節點的 gateway 現在能正確辨識「本機 GPU 目前是否
已經在忙」，並自動把併發超載的部分分派給 Swarm 裡的其他節點——這一點同時透過 dispatcher 自己的
決策日誌，以及接收節點 vLLM 的獨立執行計數器得到驗證。
